# 09 多智能体架构与通信机制设计

Type: grilling
Status: resolved
Blocked by: 02, 05

## Question

基于框架选型和Pi哲学调研，定下架构级决策：框架落地方式；论坛/黑板式agent通信的具体实现；小Loop（计划-搜索-总结-反思）的终止条件；大Loop（主持人评审：查漏补缺、盲点、矛盾检查）的放行条件；多agent并行与状态管理；上下文预算管理（给综合报告Agent喂什么、如何筛"最有价值的分析内容"）。

## Answer

用户决策（2026-08-12）两项：**编排=轻量自研（不上框架）**；**Loop终止=增益评估+硬上限（不用固定轮数、不用评分阈值）**。配套设计如下（依据02/05调研，细节在SPEC票落实）：

1. **编排基座**：Python 3.11 asyncio + AsyncOpenAI 工厂（OpenAI兼容 base_url 覆盖 deepseek/kimi/gemini/claude/硅基流动/本地/中转全部厂商，openai SDK 锁 2.x）+ FastAPI SSE。三纪律：纯函数节点、provider工厂、单一State模型——保证日后迁移 LangGraph 成本半天级。升级触发条件（写入SPEC）：持久化需求超出单表、图结构频繁演化、多人协作需统一约定。
2. **论坛通信**：进程内 ForumBoard 黑板——append-only 结构化消息列表 + asyncio.Queue 订阅（学MetaGPT"共享消息池+订阅"思想）。发言=结构化对象（agent、轮次、类型、内容、引用ID），替代 BettaFish 的"日志文件+正则tail"。论坛消息流同时经 SSE 推前端，论坛讨论过程可视化本身是产品亮点。
3. **小Loop**（单agent：计划→搜索→总结→反思）：每轮反思时 agent 结构化自答"本轮新增关键信息/剩余关键缺口"；终止=无新增或缺口清空，OR 硬上限兜底（轮数3-4、token预算）。对比 BettaFish 固定跑满反思轮不评估增益。
4. **大Loop**（论坛）：三分析agent并行（asyncio.gather）跑小Loop→产出入论坛→主持人结构化评审（缺口清单/共同盲点/矛盾清单，无矛盾不硬构造）→引导下一轮。放行=无关键未解决项，OR 最大轮数（2-3）/预算耗尽强制放行；强制放行时未解决项必须写入专报"局限性声明"——诚实呈现，呼应可核验主张。
5. **状态管理与续跑**：每轮 state 落盘（SQLite 任务状态表，Pi"效果三明治"简化版：意图→执行→结算）；任何环节崩溃可从最近轮次续跑——直接解决 BettaFish"跑3小时卡死无法重跑"的头号痛点。
6. **上下文预算**：综合报告Agent不吃全文——输入=结构化证据库（claim+引用+核验状态）+ 各agent最终摘要 + 主持人各轮决议；原始搜索结果落盘存证、不进上下文（回答PRD"给报告agent喂什么"）。
7. **异构分工**：各agent可配不同模型；主持人/仲裁建议与分析agent异构（落实08的降幻觉叙事，规避同构辩论无效的学术警告）。
