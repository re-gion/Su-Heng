## 二、关键设计决策

### 1. "示意 / 实计"双标记制度
样张最大的诚信风险是把编造的传播数据混进真实事实里。做法：**所有数字必须归入两类之一**——`示意`（棕色标签，构造数据）或 `实计`（蓝色标签，可由本报告数据算出）。KPI 卡、图表标题、图表 tooltip 三处重复标记，避免截图传播时脱离上下文。

### 2. claim 写成"经核验后的中性陈述"，网络原话单列
不把谣言原文当作条目正文，否则绿色"已证实"徽章会误读为"这条谣言是真的"。规则写在核验表顶部的规则说明块里：条目 = 中性可核验陈述；条目下方灰字给出"网络流传版本"；核验结论单独一行（支持/部分支持/不支持/信源矛盾）。

### 3. 三级徽章沿用 issues/10 的定义
已证实 = ≥2 独立信源支持；待核验 = 单源或部分支持；争议 = 信源矛盾**或核验不支持但传播广泛、保留展示**。样张里 C03（"国外酱油普遍零添加"）和 C10（"国标由海天定制"）都属于"核验不支持"，被迫归入"争议"——这暴露了一个规格问题，见下方评审问题 ①。

### 4. 信源分级用 5 档并直接显示在引用卡片上
官方/标准文本 → 主流媒体 → 门户聚合 → 行业/自媒体 → 百科（待交叉）。每张引用卡片显示分级色标，核验结论行显示"最高信源等级"。样张里刻意保留了 2 条自媒体和 1 条百科来源，用来展示低等级信源如何被标注和交叉验证（E15 与 E16 互证、E19 与 E20 冲突）。

### 5. 引文标注"原文引述 / 要点转述"
不确定是否逐字的内容一律标"要点转述"。这是本产品与"AI 幻觉式引用"的分界线，也是评审时最该被挑战的地方。

### 6. 视觉：新闻编辑室而非 SaaS Dashboard
- 底色 `#f5f4f1` 暖灰纸感，卡片纯白，1px 冷灰描边；无圆角（仅 2px）、无阴影、无渐变按钮、无紫色。
- 主色只有一个墨蓝 `#1c3f63`；语义色（绿/黄/橙红）**只用于核验徽章、情感图、转折点标记**，绝不用于装饰。
- 标题用衬线（思源宋体族，降级 Songti/SimSun/Georgia），正文用无衬线，数字与 URL 用等宽——三种字体分工对应"标题/叙述/数据"三种信息类型。
- 正文行高 1.85、栏宽 940px，中文阅读舒适区；章节用 2px 墨色下划线切分，序号用等宽字体。

### 7. 事件选择的附加价值
海天事件的核心陈述（国内外配料表不同）**本身是真的**，争的是解释权——这比"纯谣言"事件更能展示核验产品的价值：它逼出了"已证实的事实 + 不成立的推论 + 无法核验的核心指控"三种状态并存的局面，正好把三级徽章的语义撑满。

## 四、留给用户评审的问题点

### ① 三级核验是否需要扩成四级？（最高优先级）
样张里 C03、C10 都属于"证据充分地否定了某个流传说法"，但按 issues/10 的定义只能打"争议"橙红标——读者会误以为"还没定论"。
**候选方案**：(a) 维持三级，靠"核验结论：不支持"文字消歧；(b) 新增第四级 **已证伪**（建议深红/带删除线语义）；(c) 把徽章拆成两个维度——"证据强度"（强/中/弱）× "结论方向"（成立/不成立/未决）。
影响面：Agent 的核验输出 schema、渲染层、验收指标定义。**这个决定越早越好。**

### ② 官方一手单源，能否直接判"已证实"？
C09（海天是酱油国标第一起草单位）只有 1 个来源，但来自国家标准数据库。样张里我判了"已证实"并在卡片内注明。
**需要拍板**：核验规则是"≥2 独立信源"一刀切，还是"官方/标准文本等级的单源可直接采信"？后者更合理但会让"核验通过率"这一验收指标失去可比性——需要同时定义指标口径。

### ③ 传播数据拿不到真实值时，专报该怎么办？
样张用了"示意数据 + 明确标注 + 写明正式版数据来源规划"的处理。但演示站/竞赛现场若图表全是示意，产品会显得虚。
**三个选项**：(a) 保留图表但改成真实可得的口径——"报道数量随时间分布""信源类型分布"（这些能从证据库真算出来）；(b) 接热榜快照，只对新事件生效，历史事件不出声量图；(c) 维持示意但把它做成产品特性（"数据不可得时明示"）。
我的倾向是 (a)：**把"声量指数"换成"证据密度"，指标掉价但真实**，也和"可核验"卖点自洽。

### ④ "编辑判断"内容占多大比例才不越界？
第 05 节"声量低但值得注意的问题"和第 07 节研判是样张里最出彩、也最像"人写的"部分，但它们本质是 LLM 的推理产物，不是可核验事实。样张的处理是打"编辑判断"标签并写进局限性声明。
**需要确认**：C端产品是否接受"标注清楚的主观解读"？如果不接受，第 05/07 节要大幅收缩，专报的可读性会明显下降；如果接受，需要定一条硬规则（例如：主观段落必须视觉隔离 + 不得出现在执行摘要中）。

### ⑤ 单份专报的体量是否过大？
当前样张滚动高度约 11000px（约 9 屏），完整阅读 15 分钟以上。C端读者是否会读完？
**候选**：(a) 维持长报告，靠目录 + 执行摘要分层消费；(b) 拆成"速览版（摘要+核查表+结论）"与"完整版"两种渲染；(c) 默认折叠 04/06 两节。这关系到报告 IR 的结构设计，宜在 SPEC 票之前定。

## 五、已知技术限制

- 图表依赖 CDN 引入 ECharts 5.5.1（jsdelivr → unpkg → bootcdn 三级回退），**离线环境下图表会降级为文字说明**。若样张需用于无网演示，应把 echarts.min.js 内联进 HTML（约 +1MB）。
- 衬线标题依赖系统字体，Windows 上会降级到 SimSun，观感弱于 macOS 的 Songti SC。正式版若要保证一致性需自带子集化字体。
- 已验证：Chrome 桌面端 1440px / 760px 两种宽度下无横向溢出；JS 无控制台报错（仅有 file:// 协议的安全提示）；12 条 claim、32 条证据全部渲染，引用编号无悬空引用（cite → evidence 全部可解析）。
