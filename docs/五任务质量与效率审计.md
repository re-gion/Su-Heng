# 五任务质量与效率审计

## 审计范围

本审计读取本地运行数据库中 5 个已完成的标准任务，时间为 2026-09-29 至 2026-09-30。耗时来自持久化的 `task.status` 转换；模型请求数、请求时间、排队时间和失败数来自 `llm_call`。请求时间是累计值，并发时会重叠，不能直接相加当作墙钟时间。

## 结论

报告质量的主要问题在证据链闭合度，不在 HTML 排版：关键陈述大多只有单一媒体或部分支持，独立来源数通常为 0 或 1；传播关系、范围审查和报告分析审查又有缺口，因此发布门把最新两个任务正确降为证据简报。把这些内容直接改成“已证实”会损害产品的可核验承诺。

五个任务的主动耗时分别为 57.0、77.7、78.6、79.1、48.7 分钟。评论关闭的两个任务中，一个仍花了 57 分钟，另一个 48.7 分钟，说明去掉评论只能解决一部分问题；论坛调查、验证排队和报告审查仍是核心瓶颈。

## 质量问题的可操作解释

1. **主证据不足以独立互证。** 现行规则要求两个独立支持来源，或一个裁判性权威来源，才标记 `已证实`。多数任务只有单一媒体、转载或未知来源，标记为待核验是规则正确的结果。
2. **“有材料”不等于“有传播分析”。** 没有至少两个发布节点和一条可回查传播关系，不能把报告写成完整舆情专报；不能用搜索结果数或模型推测补图。
3. **范围与隐私审查会删除正文。** 被拒或未完成审查的核心段落不能继续展示；这会使报告内容变少，但这是保护普通个人和防止越权陈述的必要门槛。
4. **模型分析审查失败会留下章节缺口。** API 连接失败、输出截断或引用关系不闭合时，分析必须被拒绝或降级，不能以流畅文字掩盖失败。

## 已实施的改进

- 评论改为可选增量分支：核心事实、争议、核验和发布门先完成并发布；评论分析与核验有限并行，评论失败不阻塞核心报告，完成后再生成最终报告。
- 保留严格的 `已证实` 门槛，新增公众阅读层的 `来源直接支持`：原文已取得且支持整条陈述、但尚未独立互证时使用该状态；数据库徽章、发布门和统计口径不变。
- 将近期任务中反复出现、可识别为独立采编主体的媒体域名纳入 tier 2 信源分类；它们不会被提升为权威来源，也不会单独触发 `已证实`。
- 在报告 KPI 和核验矩阵中显示“来源直接支持”数量，避免把已取得原文且整条支持的陈述与完全没有依据的陈述混成一个“待核验”数字。

## 后续验收

关闭评论的标准任务以主动运行时间 P50 ≤ 30 分钟、P95 ≤ 45 分钟为目标。每次对照必须使用相同事件范围、深度、模型和发布门，并同时记录：阶段主动时间、累计排队时间、请求/失败/重试、关键事实覆盖、传播关系覆盖、引用闭包和最终发布等级。现有五个任务只能用于定位问题，不能证明新代码已经达到端到端时延目标；需要加载当前代码后运行同材料的新任务对照。
