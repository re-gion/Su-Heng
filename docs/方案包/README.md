> **一句话定位**：输入一个舆情事件名，自动产出一份"每个重要结论都能点回原文"的结构化舆情专报。

## 二、这个产品的三句话

1. **它是什么**：面向 C 端个人用户的舆情研究工具，开源自部署，输入事件名即出一份结构化 HTML 专报。
2. **它凭什么不一样**：第一卖点是**可核验性**——claim 级结构化引用 + 自动交叉核验 + 四级核验徽章（已证实/待核验/争议/已证伪）+ 原文快照留存。支撑点是"时间线 + 传播分析 + 历史对照"三件套、零门槛部署、异构降幻觉与合规轻数据。
3. **它的底线**：数据真实、引用可溯、不编造。**所有设计决策都要过这条线**——无引用的 claim 在渲染层被拦截，算不出真实数据的图表宁可不画。

| 11 | （原设想的）三级核验标记 | **四级**：已证实 / 待核验 / 争议 / **已证伪** | 样张暴露出"证据充分否定了流传说法"被迫归入"争议"，读者会误读为"还没定论" | 票 11 决议 1、票 10 Amendment |
| 12 | 核验规则"≥2 独立信源"一刀切 | **裁判性官方单源可直接判"已证实"**（政府通报/监管公告/标准文本/生效判决；当事方自证声明不适用；卡片注明"单源·官方"）；核验通过率按信源等级加权口径展示 | 国家标准数据库这类一手来源，要求凑第二个信源反而不合理；当事方例外是审查修订补上的 | 票 11 决议 2、审查修订 |
| 13 | 专报"有文字有图表"、可视化数据分析良好 | **图表数据强制来自证据库真实统计**（报道数量时间分布 / 信源类型分布 / 平台视角分布），拿不到真实数据就不画，降级为文字并记入局限性声明 | BettaFish 的图表数值由 LLM 转写产生，只校验结构不校验真伪——与可核验卖点直接冲突 | 调研 01、票 11 决议 3 |
| 14 | 搜索 API"配备多家兜底、质量好的优先" | 具体化为 **SearchProvider 适配器 + 能力声明 + 优先级链 + 配额感知降级 + 熔断**；零付费默认链与质量优先链均已选定 | 由全景调研给出各家真实额度/价格/中文质量/大陆连通性 | 调研 03、票 12 |
| 15 | 数据库（原文提到本地数据库即可） | **单 SQLite**，零外部依赖 | BettaFish 强制 MySQL 是其部署门槛的主要来源之一，直接劝退 C 端用户 | 调研 01/06、票 12 |
| 16 | "感觉和 BettaFish 还是有点像，要找出自己的创新点" | **第一卖点＝可核验性**；一句话区隔：BettaFish 是"重数据依赖、结论不可溯源"的舆情分析系统，本项目是"轻数据、合规优先、每句话可核验"的 C 端舆情研究工具 | BettaFish 的 442 条 issues 精确圈出四大痛点（无溯源/幻觉高/卡死不可重跑/部署难），本项目逐条对应设计 | 调研 01/06、票 08 |

**另有两项范围收缩**：

- **不做舆情走向预测**（BettaFish 宣称做）：学术上 LLM 社会模拟准确率仅 60%+ 且有系统性偏差，且预测本身不可核验，与第一卖点冲突。V1 只做"已发生传播的结构化描述 + 历史相似事件对照"。（调研 06）
- **不做新闻分发**：纯 C 端新闻时间线产品「后续」App 死于新闻资质与监管而非需求。本项目定位为个人研究工具，输出永远附原文链接。（调研 06）

## 四、方案包里已经"钉死"的关键决策一览

开工时不需要再讨论的事情：

- 编排：轻量自研，`openai` SDK 锁 2.x，asyncio + FastAPI SSE
- 前端：Vite + React + TS，SPA，事件类型→组件渲染注册表
- 存储：单 SQLite（表设计草案见架构 §6）
- Agent 定义：markdown 数据文件（frontmatter 声明能力，正文即系统提示词）
- 五个角色：事实调查 / 媒体传播 / 历史洞察 / 论坛主持人 / 综合报告（+ 一个非 agent 的核验器）
- 小 Loop 终止：增益自评 + 硬上限；大 Loop 放行：主持人评审 + 轮数/预算上限
- 核验：四级徽章（作用于条目正文的被核验陈述）+ 逐证据**结构化五值关系**（支持/部分支持/材料未涉及/材料否定/材料内部矛盾）+ **D1–D11 全量决策表**（有反证或内部矛盾一律不判绿，含同主体时序覆盖规则）+ 信源五级 + 官方单源规则（限裁判性权威，当事方不适用）+ 独立信源按采编主体归并 + 加权通过率口径 + **以 claim 为原子的核验单位**
- 证据：先入库后引用 + 抓取状态机（discovered/fetched/fetch_failed，条件不变量落 DDL CHECK）+ 引述三类型（原文引述必须精确匹配校验，**校验失败拒收重出、不改标签放行**；搜索摘要须与摘要等值）+ SSE 事件全量落 event_log（heartbeat 除外，它是 SSE 注释行）
- 报告：LLM 产 IR JSON + 确定性渲染 + **权威字段（正文/徽章/结论/引用卡片）由渲染层按编号从数据库回填，报告 Agent 只排版** + 引用闭包与摘要蕴含校验 + 速览/完整双版 + 单文件自包含 HTML（不内嵌完整快照；V1.5 提供证据包 ZIP 导出）
- 续跑：轮次检查点 + 效果三明治（意图→执行→结算）
- 合规：默认只碰公开数据，Cookie 插件 V2 且默认关闭
- 分期：M0（单 agent 竖切）→ V1（参赛 MVP）→ V1.5（数据纵深）→ V2

## 七、两轮对抗性审查的修订记录

方案包定稿当日由第二个 AI（Codex）做了两轮对抗性审查，报告存于 `审查/`。

### 7.1 第一轮（`审查/codex-对抗性审查报告.md`）

第一轮共 **23 条：5 项 P0、15 项 P1、3 项 P2**（此前台账误记为"12 项 P1、共 20 条"，第二轮复审指出并已按报告正文更正——按错误计数销项会漏掉异步安全、历史数据层、复杂度估算三项 P1）。经逐条核实后绝大多数成立，已全部落实修订；文中相关位置均标注"审查修订/审查 P0/P1 修复"。要点：

**P0 修复（不修就开不了工）**：
1. 数据库改**双 ID 体系**（全局 pk + 任务内 local_id），修复"第二个任务主键冲突"；枚举落 CHECK、外键 CASCADE、删除生命周期补全（架构 §6）。
2. **"已证伪"的判定对象显式化**：徽章永远作用于条目正文（`statement_kind` 分 fact/rumor 两种条目写法 + 渲染层一致性守卫），辟谣红标不会再盖在真话旁边（SPEC §4.4、05 §0.2）。
3. **证据抓取状态机与引述三类型**：搜索摘要只能标"搜索摘要"、"原文引述"必须在已抓原文中精确匹配（SPEC §5.1/§4.4）。核验门槛经用户拍板取**宽松口径**：摘要互证可判"已证实"，但卡片如实注明"原文未取得"。
4. **官方单源规则收紧**为"裁判性权威且非当事方"（当事方声明只能证实"作出过声明"）；**独立信源按原始采编主体归并**，一稿多站不再算多源（SPEC §4.4/§5.5、05 §4.3）。
