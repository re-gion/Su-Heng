# Codex 对抗性审查报告：舆情 Agent 开工级方案包

> 审查日期：2026-08-12  
> 审查范围：`docs/方案包/` 五份文档、原始 PRD、规划地图、14 张决策票、6 份调研报告、样张及设计说明  
> 审查方式：逐文档交叉核对；对 LangSearch、百度千帆、微博诉蚁坊案、DailyHotApi、公开数据集许可、SQLite 并发等关键事实做外部复核  
> 边界：本报告是技术与产品合规风险审查，不替代正式法律意见。

## 一、总体结论摘要

这套方案包的产品方向可以保留，但“拿着就能直接开工、没有悬而未决的关键决策”不成立。当前最严重的问题不是文档少，而是几处核心承诺在数据模型和运行时协议上无法兑现：第二个任务就会发生主键冲突；“已证伪”究竟否定 `claim.text` 还是 `rumor_text` 没有建模；搜索摘要可以在未取得原文、未生成快照的情况下进入证据链；“官方单源”和“不同域名”规则会把当事方声明、同源转载误判成已证实；SSE 声称可从 SQLite 全量补发，但 schema 中没有事件日志表。

外部事实链也存在实质错误。LangSearch 已公开免费层 1 QPS、60 QPM、1000 QPD，并非“官方未公开 QPS/总量”；百度千帆普通搜索约 50 次/日且单价已公开；微博诉蚁坊案的关键事实包括绕过访问权限并获取非公开数据，不能简化为“抓公开微博数据做分析就判赔 528 万”；DailyHotApi 的 MIT 许可只覆盖代码，不替代上游平台的数据许可；`weibo_senti_100k` 当前没有可确认的再分发许可证。

## 二、六个审查轴结论

| 审查轴 | 结论 | 核心理由 |
|---|---|---|
| 1. 内部一致性 | **不通过** | 四级徽章、编辑判断隔离、双版渲染已在文字层基本传播，但“已证伪”的判定对象没有进入 schema；6+1 角色的独立配置没有进入 `.env` 用户契约；“单文件可转发”与外置快照链接互相冲突。 |
| 2. 事实可靠性 | **不通过** | 免费额度、计费、判例要旨、代码许可与数据合规之间存在多处已证实的错误或过度概括。 |
| 3. 技术可行性 | **不通过** | 方向可实现，但现有 schema、SSE、SQLite 并发、异步故障隔离、预算上限不足以支撑文档承诺。 |
| 4. 完整性 | **“拿着就能开工”不成立** | 缺完整 IR schema、API 请求/响应契约、核验 prompt、证据状态机、事件持久化协议、暂停/取消语义和可执行预算默认值。 |
| 5. 风险盲点 | **不通过** | 热榜与公开数据集被过度宣称为合规；未覆盖 SSRF、网页提示词注入、快照 XSS、公开演示站的名誉/隐私/删除纠错机制。 |
| 6. 过度设计与能力匹配 | **失衡** | 一面在 M0 同时引入动态 Agent/Skill、效果三明治、SSE 补发、快照、核验和 IR；另一面又把完整编排估为 200–400 行、迁 LangGraph 估为半天，复杂度估算明显失真。 |

## 三、发现清单（按严重级别排序）

### P0 阻塞

**[P0阻塞] 任务内可读 ID 与全局主键冲突，第二个任务即可能写库失败** ｜ 位置：`02-系统架构设计.md` §6，`evidence`/`claim`/`claim_evidence` 表（约第 498–554 行）｜ 问题陈述：文档把证据与 claim 编号定义为任务内的 `E001`、`C07`，但 `evidence.id` 和 `claim.id` 却是全库单列主键；`claim_evidence` 也只按这两个 ID 建外键，没有 `task_id`。｜ 失败场景：第一个任务写入 `E001`、`C01` 后，第二个任务再次从 `E001`、`C01` 编号会触发 `UNIQUE constraint failed`；如果改成全局递增，又与报告内短编号及任务内引用语义冲突。｜ 证据：schema 注释明确写 `E001（任务内可读编号）`，同时定义 `id TEXT PRIMARY KEY`；SPEC 的示例也使用 `E09`、`C07` 这种任务内编号。｜ 修复建议：物理主键使用全局 UUID/ULID，例如 `evidence_pk`、`claim_pk`；另设 `(task_id, local_id)` 唯一约束供报告显示。`claim_evidence` 必须引用物理主键，或携带 `task_id` 并使用复合外键；增加“两项连续任务均从 E001/C001 开始”的集成测试。

**[P0阻塞] “已证伪”没有明确判定对象，徽章可能否定错误的句子** ｜ 位置：`01-产品SPEC.md` §4.4、§5.2–§5.3；`02-系统架构设计.md` §6 的 `claim` 表 ｜ 问题陈述：SPEC 一方面要求 `claim.text` 必须是“经核验后的中性可核验陈述”，另一方面把“已证伪”定义为“证据充分否定该流传说法”；schema 同时保存 `text` 与 `rumor_text`，却只有一组 `badge/verdict`。核验伪代码问的是“原文是否支持这条 claim”，没有声明核验 `text` 还是 `rumor_text`。｜ 失败场景：系统把中性陈述“日本酱油并非普遍零添加”写进 `text`，把网络说法放进 `rumor_text`；若核验器核验 `text`，它应得到“支持/已证实”，若为了展示辟谣而打“已证伪”，红色徽章在视觉上却会变成“这句中性陈述不成立”。核心核验表出现方向性错误。｜ 证据：SPEC 第 209–222 行、350–376 行；schema 第 524–541 行没有 `verdict_target`、命题方向或双命题结果。票 10 Amendment 只增加第四级，没有补数据语义。｜ 修复建议：把“事实命题”和“流传说法”建成两个明确对象，例如 `assertion` 与 `rumor_assertion`，每个对象各有 verdict；或者规定徽章永远作用于屏幕上完整展示的 `evaluated_statement`，辟谣条目正文必须直接写待否定命题。IR、核验 prompt、数据库和 UI 统一该规则，并用“真事实 + 假推论 + 真正争议”三类回归样例验证方向。

**[P0阻塞] 证据链允许“未取原文、无快照、无精确引文”的结果进入核验，第一卖点不可强制** ｜ 位置：`01-产品SPEC.md` §4.4、§5.1；`02-系统架构设计.md` §4.2、§6、§7.3；`04-搜索与数据源配置指南.md` §5 ｜ 问题陈述：用户侧规格宣称引用卡片必须有原文关键句和快照，缺一不可渲染；实际小 Loop 只搜索后直接 `bulk_add(results)`，没有调用 `fetch_page`，并把搜索 API 的长摘要列为 P0 原文来源。数据库中的 `content_text`、`snapshot_path`、`claim_evidence.quote` 全部可空，也没有 verbatim 引文的字符偏移、所对应内容哈希或确定性子串校验。｜ 失败场景：LangSearch/博查的摘要被当作“原文”入库，模型基于摘要生成 claim 与引文；原网页未抓取或已变更，快照为空，用户点击只能看到 URL，无法证明引文在原文中出现。系统仍可能因 evidence_id 存在而通过渲染，形成“真实链接 + 错引内容”的正是产品声称要解决的幻觉。｜ 证据：SPEC 第 226–236、338–346 行；架构伪代码第 322–330 行；schema 第 511–513、549–550 行；抓取链第 702–709 行。｜ 修复建议：引入 `discovered → fetched → extracted → quote_verified → eligible` 证据状态机；搜索摘要只能用于候选发现，不得作为“原文引述”的依据。正式 claim 只能绑定 `eligible` 证据；verbatim 必须在固定版本 `content_text` 中精确匹配并保存起止偏移与 `content_sha256`。无法抓取原文时只能标“搜索摘要/要点转述”，不得获得“已证实”，且必须在报告中显式降级。

**[P0阻塞] “官方单源 + 不同域名”规则会系统性制造错误的绿色“已证实”** ｜ 位置：`01-产品SPEC.md` §4.4、§5.5；`02-系统架构设计.md` §6 设计说明 1；决策票 10 Amendment ｜ 问题陈述：L1 同时包含政府/标准文本和企业官方声明，却规定 L1 单源可直接“已证实”；多源独立性又实际按不同 `source_domain` 计数。企业对自身争议的声明不是独立事实裁判者；同一通讯稿被几十个域名转载也不是几十个独立信源。文档虽说同集团或转载应归并，schema 却没有 `publisher_entity`、`origin_url`、`syndication_group`、`source_role` 等字段来实现。｜ 失败场景：涉事企业发布一份自证声明，系统因 L1 单源将“企业否认违法”直接标绿；声明随后被新浪、网易、凤凰转载，系统按三个域名再次认定多源互证。评委点回去会发现所有来源都来自同一当事方。｜ 证据：SPEC 第 219、379、393–401 行；schema 仅有 `source_domain/source_tier`，独立信源数被定义成不同域名计数（架构第 620 行）。｜ 修复建议：把“来源权威等级”与“对该命题的角色”分离。只有具有管辖权的监管结论、正式判决、生效标准原文等可进入“权威单源规则”；企业声明必须标 `party_statement`，只能证明“企业作出过该声明”，不能证明声明内容为真。增加来源血缘/转载归并字段和规则，独立性按原始采编主体与上游出处计算，并用“一稿多站”和“当事方声明”建立负向测试。

**[P0阻塞] SSE 声称可全量补发，但 schema 中没有可补发的事件日志** ｜ 位置：`01-产品SPEC.md` §3.3；`02-系统架构设计.md` §5、§6、§13；`03-实施路线图.md` M0-7 ｜ 问题陈述：协议要求全局单调 `seq`、断线后 `since_seq` 补发，并声称“内存环形缓冲 + SQLite 全量”；但数据库只有 `forum_message`，没有统一 `event_log` 表，也没有持久化 `seq`。`agent.status`、`search.result`、`evidence.added`、`verify.progress`、`report.section`、预算和错误事件均无法从 SQLite 重建原始序列；历史回放与实时订阅之间的原子切换也未定义。｜ 失败场景：环形缓冲覆盖后，用户刷新页面，服务端只能补论坛消息，证据、核验和报告章节事件永久缺失；更常见的是客户端先读历史、后订阅队列，两步之间产生的事件落入空窗，页面看起来“卡住”或计数不一致。｜ 证据：架构第 428–460 行承诺事件协议；第 478–616 行全部 schema 无事件表；第 939 行才把缓冲大小留作实现期决定。｜ 修复建议：新增 append-only `event_log(task_id, seq, event_type, ts, payload)`，`UNIQUE(task_id, seq)`；业务状态提交和事件写入要么同一事务，要么采用 outbox。定义重连算法：先取得高水位 H，再订阅实时流，补发 `(since_seq, H]`，随后只接收 `>H`；SSE 同时发送标准 `id:` 字段并支持 `Last-Event-ID`。用“历史读取与订阅切换时并发写事件”的集成测试证明无丢失、无重复。

### P1 重要

**[P1重要] SQLite 只写了 WAL，没有设计三 Agent 并发写入策略** ｜ 位置：`02-系统架构设计.md` §3.3、§4、§6；`03-实施路线图.md` V1-3 ｜ 问题陈述：三个 Agent 会并发写 evidence、claim、forum、task_state 和事件，方案只声明 WAL。SQLite 官方文档明确：WAL 允许读写并发，但同一时刻仍只有一个 writer；应用仍应准备处理 `SQLITE_BUSY`。文档没有连接模型、单写者队列、`busy_timeout`、事务边界、写重试或 checkpoint 策略。｜ 失败场景：三个 Agent 搜索完成后同时批量入库，论坛与 SSE 又同步落盘，短事务叠成长锁，出现 `database is locked`；若 `asyncio.gather` 让异常上抛，整个轮次失败。｜ 证据：架构第 271、288–304、480 行；SQLite 官方 [WAL 并发说明](https://www.sqlite.org/wal.html#concurrency) 明确“only one writer at a time”，并提供 [`busy_timeout`](https://sqlite.org/c3ref/busy_timeout.html)。｜ 修复建议：M0 即采用单写者队列或显式写串行化；所有批量写短事务化；配置 `busy_timeout` 与有限退避；外部网络/LLM 调用绝不能包在事务内；固定 SQLite 最低版本并覆盖 2026 年 WAL 修复版本；增加 3 Agent × 多任务并发压力测试和崩溃恢复测试。

**[P1重要] Token、搜索调用数、claim 数和耗时没有硬数字，预算器只有名词** ｜ 位置：`01-产品SPEC.md` §3.2；`02-系统架构设计.md` §4.2、§8.4；`03-实施路线图.md` V1 验收/R1/R5；`04-搜索与数据源配置指南.md` §2.2 ｜ 问题陈述：只给事实 Agent 一个 `token_budget: 60000` 示例，没有 quick/standard/deep 的全局默认值、每角色输入/输出上限、每轮 query 上限、最大 claim 数、最大证据正文长度、核验批大小、单次费用和目标 P50/P95 延迟。`plan.queries` 没有长度约束，核验又按 claim 逐条调用。｜ 失败场景：按文档默认标准模式，若每 Agent 每小轮仅 3 个 query，最大搜索已是 `3 Agent × 2 外轮 × 4 内轮 × 3 query = 72 次`；深度模式为 108 次，降级链失败时还会放大。标准模式在核验与报告前已有约 56 次 LLM 调用，若再核验 30 个 claim、生成 10 个板块，总调用可接近 96 次。成本与延迟可能远超“几元、几分钟”，也可能一天内耗尽百度补充额度。｜ 证据：架构第 286–305、313–348、365–420、765–771 行；配置指南只写“一次完整专报大约几十次搜索”。以上数字是按现有上限的保守推演，文档本身没有测算表。｜ 修复建议：在开工前给三档模式建立预算表，至少规定 `max_queries_per_round`、`max_search_calls`、`max_fetches`、`max_claims`、`max_evidence_chars`、`max_verifier_calls/batch`、各角色 token 和费用上限、P95 超时；先用一个真实事件做 dry-run 计量，再决定默认轮数与模型组合。

**[P1重要] 免费搜索链的额度与计费事实有明确错误，配额感知无法按文档实现** ｜ 位置：`04-搜索与数据源配置指南.md` §3.1、§3.4、§6、§10；`02-系统架构设计.md` §7.2 ｜ 问题陈述：LangSearch 被写成“官方未公开 QPS/总量上限”，但官方已公开免费层 1 QPS、60 QPM、1000 QPD。百度千帆“1500 次/月”属实，但实际按天发放约 50 次/日，普通搜索标准版/增强版价格也已公开，文档仍写“单价未能核实”。｜ 失败场景：实现者只做日/月计数而不做 1 QPS 限速，并行 query 会持续收到 LangSearch 429；主力失败后，一次 50–70 次搜索可能吃完百度当天额度，竞赛第二次演示直接降级。｜ 证据：[LangSearch Pricing](https://langsearch.com/pricing)、[LangSearch API Limits](https://docs.langsearch.com/limits/api-limits)；百度千帆[普通搜索文档](https://cloud.baidu.com/doc/qianfan/s/2mh4su4uy)与[计费页](https://cloud.baidu.com/doc/qianfan/s/1mh4sv6c4)列出约 50 次/日、标准版 0.036 元/次、增强版 0.072 元/次。｜ 修复建议：修正文档并把 QPS/QPM/QPD、日/月重置边界、价格、接口版本写进可版本化 `QuotaSpec`；SearchChain 增加 provider 级令牌桶，不只是调用后计数；验收要覆盖 1 QPS 并发限速和日额度耗尽。

**[P1重要] 微博诉蚁坊案被过度压缩，导致合规边界既过度恐吓又错误放行** ｜ 位置：`README.md` 原 PRD 修正项 1；`01-产品SPEC.md` §6.2；`04-搜索与数据源配置指南.md` §8.4 ｜ 问题陈述：方案把该案概括成“抓取微博公开数据做舆情分析，判赔 500 万 + 28 万，与本场景几乎同款”，并称系统性囤库是加重情节。可核对的裁判要旨包含更关键的事实：利用技术手段破坏或绕开访问权限，抓取包括非公开数据在内的平台数据，影响数据安全、展示规则与正常运营；即便是公开数据，也要结合规模、价值和实质替代逐案判断。现有来源不支持把“历史囤库”单独表述为裁判认定的加重情节。｜ 失败场景：团队可能误以为“只要是公开榜单就零风险”，忽略规模、条款和商业替代；也可能把合法的低频公开信息利用一概视为违法，做出错误产品决策。｜ 证据：[全国法院知识产权典型案例汇编](https://www.ipeconomy.cn/pdf/230509.pdf) 第 17 页的案情与裁判要旨；案号和 528 万结果成立，但方案遗漏了决定违法性的关键事实。｜ 修复建议：重写判例摘要，删除“几乎同款”和无直接依据的“加重情节”断言；把审查清单改为数据公开性、访问控制、获取手段、规模频率、服务器负担、商业替代、个人信息、存储与再分发八项，并在发布前由专业律师复核。

**[P1重要] 面向 C 端的名誉、隐私、纠错与删除风险没有进入产品边界** ｜ 位置：`01-产品SPEC.md` §6；`03-实施路线图.md` V1.5 演示站 ｜ 问题陈述：合规章节几乎只讨论“怎么抓数据”，没有限制用户针对普通个人、未成年人、未证实刑事指控或隐私事件生成专报，也没有报告保留期限、删除、纠错、申诉、去索引、日志脱敏和演示站 takedown 机制。｜ 失败场景：用户输入普通人的网名或学校事件，系统把低质量指控做成可转发 HTML 并长期保存；即使打了“待核验”，聚合和结构化展示本身也可能扩大伤害，公开演示站收到投诉后没有定位和删除链路。｜ 证据：SPEC 第 420–468 行只覆盖数据获取和模型拒答；报告被设计为永久保存（第 153 行）；演示站规划没有内容治理接口。｜ 修复建议：开工前定义允许/拒绝的事件范围、普通个人与未成年人保护、敏感字段脱敏、报告 TTL、删除与更正接口、审计日志、公开分享默认关闭、演示站人工审核和 takedown SLA。对高风险指控，默认只呈现权威公开材料，不生成编辑判断。

**[P1重要] 自研选型依据低估的恰好是本方案已经要求的能力，200–400 行和半天迁移没有证据** ｜ 位置：README 修正项 3；`02-系统架构设计.md` §0、§1.3、§10–§11；调研 05 §4 ｜ 问题陈述：自研被论证为一个 while + gather + list，但方案同时要求持久事件日志、断线重连、崩溃续跑、效果三明治、暂停取消、预算、配额、熔断、跨 provider 兼容、部分失败、报告流式和 SQLite 并发。调研自己承认 200–400 行和框架迁移均未实测；“纯函数节点”也无法自动迁移数据库副作用、事件顺序和恢复语义。｜ 失败场景：开发者按 200–400 行心理预期开始，真正复杂度在 M0-7/M0-9 集中爆发；等到改投 LangGraph 时，state、checkpoint、事件和副作用模型不一一对应，半天无法完成，比赛工期被选型返工吞噬。｜ 证据：调研 05 第 184–191 行明确标注估算未实测；方案中的恢复与事件设计已远超“简单固定拓扑”。｜ 修复建议：不必立即推翻自研，但在开工前做两天技术 spike：用同一最小流程分别验证“自研 + SQLite event log”和“LangGraph checkpoint + 自定义 SSE”，实测代码量、恢复、取消和调试成本后再冻结。删掉“保证半天迁移”的承诺，改成迁移前置条件与验收清单。

### P2 建议

**[P2建议] M0 的 CLI 完成信号与目录结构不一致** ｜ 位置：`02-系统架构设计.md` §9；`03-实施路线图.md` M0-3 ｜ 问题陈述：路线图要求运行 `python -m yuqing.scripts.llm_ping analyst_a`，目录树却把 `scripts/` 放在 `backend/scripts/`，不在 `backend/yuqing/` 包内。｜ 失败场景：开发者照命令执行得到 `No module named yuqing.scripts`，在开工第三步就怀疑环境或包结构。｜ 证据：架构第 780–832 行与路线图第 51 行直接矛盾。｜ 修复建议：二选一：把脚本放到 `backend/yuqing/scripts/` 并加 `__init__.py`，或把命令改为 `python backend/scripts/llm_ping.py`/pyproject console script；所有路线图命令在干净环境实际跑一遍。

**[P2建议] 数据库草案缺少基础约束和删除生命周期，后期会放大脏数据** ｜ 位置：`02-系统架构设计.md` §6 ｜ 问题陈述：badge、verdict、status、source_tier 没有 CHECK；外键没有说明 `PRAGMA foreign_keys=ON`；没有 `ON DELETE` 策略；报告“永久保存”但没有任务删除如何联动快照文件。｜ 失败场景：拼写错误的 `verifed` 状态入库后前端无法渲染；删 task 后残留 claim、快照或报告文件；数据库与文件系统逐渐失配。｜ 证据：现有建表 SQL 只用注释表达枚举和关系。｜ 修复建议：把枚举约束落进 SQL 或由迁移层统一校验，启动时强制外键，定义任务删除/归档事务与文件垃圾回收，并用迁移测试覆盖。

**[P2建议] M0/V1 同时引入的抽象过多，应以验证核心卖点为中心再展开** ｜ 位置：`02-系统架构设计.md` §1–§3、§9；`03-实施路线图.md` M0/V1 ｜ 问题陈述：对入门开发者，M0 已同时包含五层 import 契约、Markdown Agent loader、渐进 Skill、工具 registry、SSE 重放、效果三明治、快照、LLM 核验和 IR 渲染；V1 又一次性扩到 4–5 个搜索 provider。部分抽象在首个“claim—原文—核验—报告”端到端路径稳定前没有验证价值。｜ 失败场景：大量时间花在 loader、registry、provider 配置和 UI 事件组件，核心的引文精确匹配与误判率迟迟没有基线；比赛前得到的是架构骨架而不是可信报告。｜ 证据：路线图 M0-1 至 M0-9 和 V1-1 至 V1-8 的范围；用户约束是入门水平、小额预算。｜ 修复建议：把真正的 M0 缩为固定一个 Agent、一个搜索 provider、一个模型、同步 CLI、SQLite 证据链、静态 HTML；先在 2 个事件上人工核验 20 条 claim。准确性达标后再依次加入 SSE、并发、动态 Agent/Skill、恢复和多 provider。保留分层边界，但暂不实现未被使用的扩展机制。

## 四、建议的开工前最小修订门

以下项目全部完成后，才建议进入正式编码：

1. 修正 evidence/claim 主键与 `claim_evidence` 外键。
2. 定稿“已证伪”的判定对象和双命题数据模型。
3. 定义证据状态机、原文抓取资格、精确引文定位与快照导出形态。
4. 重写官方单源与独立信源规则，加入来源角色和转载血缘。
5. 增加持久化 event log，并写清 SSE 无缝重连算法。
6. 给出 quick/standard/deep 的硬预算数字与一次真实事件测算。
7. 补齐 IR、AgentDefinition、OpenAPI、verifier/reporter prompt 四份可执行契约。
8. 修正搜索额度、判例和数据许可表述，建立逐源合规清单。
9. 加入 SQLite 单写者、异步取消/部分失败和公开演示站安全模型。
10. 用两个真实事件做端到端人工抽检，再决定自研编排是否继续。

## 五、总体判定

**总体判定：修订 P0-P1 后开工。**

理由：产品定位、轻数据路线、Vite + React + FastAPI、确定性报告渲染等大方向仍可用，没有必要把整套方案推倒重来；但当前 P0 会直接造成第二任务写库失败、核验徽章语义错误、证据链无法强制和 SSE 无法兑现。P1 又覆盖并发、预算、外部事实、合规、安全与开工契约。若直接按现文档编码，最可能的结果不是“小修小补”，而是在 M0-7 至 V1-5 之间集中返工。先关闭上述 P0/P1，再进入实现，成本明显低于边写边重做。
