# 03 · 实施路线图

> 本文回答"先做什么、什么算做完、哪里会出问题"。
> 阶段划分与验收标准来自票 13，本文在其基础上补充开发顺序与风险对策。
> 撰写日期：2026-08-12

---

## 0. 总体原则

1. **每个阶段都必须有可演示交付物**——不做"半年后一次性上线"的规划（票 13）。
2. **M0 → V1 → V1.5 串行推进**，每阶段结束用真实舆情事件做一次全流程演示验证。
3. **竖切优先于横切**：先把一条最窄的路径从头打通（一个 agent 从输入到报告），再横向复制成三个 agent。这是票 05 §5 的明确建议，也是入门开发者最不容易卡死的路径。
4. **不可核验的功能一律后移**：任何"看起来炫但数据来源说不清"的功能（示意图表、情感百分比、走向预测）都不进 V1。

## 2. M0 · 骨架竖切

### 2.1 范围（票 13）

单 agent（事实调查）+ 证据库（SQLite，快照存证）+ LLM 交叉核验（四级徽章）+ 速览版 HTML 报告 + SSE 流式 + 每轮 state 落盘。

### 2.2 验收标准（票 13，逐条可测）

- [ ] **零配置可跑**：只填一个低成本 LLM 的 key + 一个免费搜索 key，输入事件名即可产出报告。
      > 口径说明："零配置"指零外部服务依赖（无 MySQL、无 Docker、无爬虫、无浏览器），并非零 API key——LLM key 必填至少一个。
- [ ] 产出的速览报告中，**每个引用标都可点击**，能跳到证据卡片并显示来源、日期、原文关键句、URL、快照。
- [ ] **进程中断后可从最近状态续跑**：跑到一半 `kill -9`，重启后点"续跑"能接着走完并出报告。
- [ ] **重要 claim 100% 绑定 evidence_id**：随机抽 20 条 claim，全部能在证据库中查到对应记录；构造一条无引用 claim，验证它被渲染层拦截。

### 2.3 开发顺序（1-agent 流式竖切，9 步）

> 每一步都以"能跑给自己看"结束，不允许出现连续两步都没有可运行结果的情况。

| 步骤 | 内容 | 完成信号 |
|---|---|---|
| **M0-1** 工程骨架 | 仓库目录（见架构 §9）、`pyproject.toml`、FastAPI hello、Vite hello、`import-linter` 契约文件、`AGENTS.md` | `uvicorn` 起得来，访问首页看到 React 页面；`lint-imports` 通过 |
| **M0-2** 存储层 | `schema.sql` 建全部表（双 ID 体系 + CHECK 约束 + event_log，架构 §6）、`db.py` 连接与迁移（WAL/foreign_keys/busy_timeout）、pydantic 模型 | 跑一个脚本，能写入并读回一条 `task` 与一条 `evidence`；**连续创建两个任务，各自证据从 E001 编号且互不冲突** |
| **M0-3** LLM 工厂 | `core/llm/factory.py` + 角色配置加载 + usage 统计 + tenacity 重试 | CLI 脚本 `python -m yuqing.scripts.llm_ping analyst_a` 返回模型回复与 token 数 |
| **M0-4** 搜索与抓取链 | `SearchProvider` 抽象 + LangSearch 适配器（含 1 QPS 令牌桶）+ `FetchProvider` 抽象 + httpx/trafilatura 兜底 + SSRF 基础防护（架构 §7.4）+ 配额计数 | CLI 搜一个关键词，打印归一化后的 `SearchResult` 列表；对其中一条取全文成功；对 `http://127.0.0.1` 的抓取被拒绝 |
| **M0-5** 证据库 | `evidence_store`：入库（单写者队列，架构 §6.1）、URL 归一化去重、抓取状态机（discovered/fetched/fetch_failed）、快照 gzip 落盘、信源分级表 | 搜一个词 → 库里出现 N 条证据、`data/snapshots/` 出现 N 个文件、重复搜同一词不新增记录 |
| **M0-6** 单 agent 小 Loop | `agents/runtime.py` + `definitions/fact_investigator.md` + 业务工具（search/fetch/evidence_write/claim_write）+ 增益自评终止 | 命令行跑一个真实事件，控制台看到"计划→搜索→总结→反思"，最终库里有一批 claim 且都绑定了 evidence_id，终止原因被打印 |
| **M0-7** SSE 竖切 | `core/events.py` 事件信封 + `event_log` 持久化 + `/api/tasks` + `/api/tasks/{id}/events`（`since_seq` / `Last-Event-ID` 重连契约，架构 §5.1）+ 前端 `useTaskStream` + 三个事件的渲染组件 | 浏览器里实时看到 agent 状态、证据流、轮次判定；刷新页面靠 `since_seq` 无缝补上，seq 无缺无重 |
| **M0-8** 核验与徽章 | `verification.py`：逐 claim 比对引用原文（核验对象 = claim 正文那句话，prompt 与金样例见 05-核心契约）→ 结论 → 独立信源数（按采编主体归并）/最高信源等级 → 四级徽章；指标计算 | 报告页每条 claim 显示徽章；用"真事实 / 假流传说法（rumor 条目）/ 真正争议"三类样例验证徽章方向全部正确 |
| **M0-9** 速览报告渲染 + 续跑 | `render/ir.py` + `validator.py`（无引用 claim 拦截、`illustrative` 拦截）+ 速览版 HTML 模板 + 引用卡片交互；`resume.py` + 轮次检查点 | 端到端出一份速览报告；中途 kill 进程后续跑成功 |

### 2.4 M0 阶段的取舍（明确不做）

- 不做论坛、不做主持人、不做并行；
- 不做完整版十板块，只做"执行摘要 + 关键事实核查表 + 局限性声明"三块；
- 不做配置页（改 `.env` 即可）；
- 不做 PDF、不做图表。

### 2.5 M0 的两道质量门（审查后新增，用户已确认）

1. **准确性基线门**（过 M0-8 后、进 M0-9 前）：用 2 个真实事件跑核验链路，人工抽检 20 条 claim 逐条回原文核对，记录"徽章方向错误率 / 引用错配率"作为项目质量基线；不达标（如徽章方向错误 >1 条）先修核验再继续。**核心卖点的准确性不达标时，继续堆功能没有意义。**
2. **编排复评门**（M0 收尾）：对照架构 §11 的 LangGraph 触发条件，用 M0 实测复杂度（实际代码行数、调试痛点、事件/续跑实现成本）重新回答"自研编排是否继续"——M0 本身就是自研路线的最小验证，这道门把"200-400 行"从估算变成实测。

另：M0 验收补充一条——**用 1 个真实事件做 dry-run 计量**（搜索次数、LLM 调用数、token、费用、耗时），校准架构 §8.4 预算表的默认值。

## 3. V1 · 参赛 MVP

### 3.1 范围（票 13）

三分析 agent 并行（事实调查 / 媒体传播 / 历史洞察-按需回溯模式）+ 论坛黑板 + 主持人评审（增益评估 + 硬上限双 Loop）+ 综合报告 agent；完整版专报（十板块、四级核验、速览/完整双版、传播图表用证据库真实口径）；SSE 论坛过程前端可视化；配置页（多 LLM 角色三元组 + 搜索 API 多家兜底）；搜索 API 用户文档。

### 3.2 验收标准（票 13，逐条可测）

- [ ] **引用覆盖率 100%**（重要 claim）——由 `metrics.py` 自动计算并在报告页展示，**同时展示候选 claim 总数 / 被拦截数及原因 / 降级为非重要数**（SPEC §5.6，防"过滤后恒等式"）。
- [ ] **核验通过率按信源加权口径展示**——报告中同时显示未加权与加权两个数，注明口径与"官方单源（裁判性、非当事方）可判已证实"的规则。
- [ ] **故障隔离可演示**——人为让一个 agent 的 provider 持续报错，其余两个 agent 正常完成并出报告（架构 §4.5）。
- [ ] **局限性声明必出**——任何一次运行都不允许该板块为空。
- [ ] **断点续跑可演示**——现场 kill 进程后续跑成功。
- [ ] **单次完整分析在可配 token 预算内完成**——预算条不超限，超限时正确触发强制放行并写入局限性声明。
- [ ] **非技术用户按 README 能在 10 分钟内跑出第一份专报**——找一位没参与开发的人实测计时。

### 3.3 开发顺序（9 步）

| 步骤 | 内容 | 完成信号 |
|---|---|---|
| **V1-1** agent 定义数据文件化 | 把 M0 硬编码的提示词全部搬进 `.md`；补齐 `media_propagation` / `history_insight` 定义与 skills（检索词工程、信源分级、时间线构建） | 改提示词不用改代码；三个 agent 定义都能被 loader 正确解析 |
| **V1-2** 论坛黑板 | `ForumBoard`（append-only + Queue 广播 + SQLite 持久化）+ `forum_post` / `forum_read` 工具 + `forum.message` SSE | 单 agent 也能发言，前端看到讨论流 |
| **V1-3** 三 agent 并行 | TaskGroup 监督并行跑三个小 Loop（五态结果、故障隔离、取消令牌，架构 §4.5）；每 agent 独立预算；3 agent 并发写库压测（架构 §6.1 单写者队列） | 三个面板同时滚动；总耗时明显低于串行；单 agent 失败不影响其余 |
| **V1-4** 主持人与大 Loop | `moderator` 定义 + 结构化评审 schema + 放行判定 + directives 注入 + 强制放行写局限性声明 | 能看到"第 1 轮评审 → 给出缺口 → 第 2 轮 → 放行"完整过程 |
| **V1-5** 报告 agent 与完整 IR | 上下文裁剪（证据库摘要 + agent 摘要 + 主持人决议）+ 十板块 IR schema + 分章节生成（无依赖章节并发）+ 四类失败分类重试与最优候选兜底 | 完整版报告十板块齐全，单章生成失败不导致整体失败 |
| **V1-6** 真实口径传播图表 | 从证据库算三张图（报道数量时间分布 / 信源类型分布 / 平台视角分布）+ 数据不足时降级为文字并记局限性 | 图表数值能在证据库里逐个对上；人为删掉证据后图表正确降级 |
| **V1-7** 报告渲染完善 | 速览/完整双版切换、四级徽章筛选、引用悬浮预览与跳转高亮、左侧目录滚动高亮、打印样式、图表库与字体内联 | 断网状态下打开 HTML 文件，图表与字体正常 |
| **V1-8** 搜索链扩充与配置页 | 补齐 4-5 家 provider 适配器（LangSearch / 百度千帆 / 智谱 / Tavily / Serper）+ 配额感知降级 + 熔断；配置页（角色三元组、搜索优先级、连接测试） | 故意把主力 key 填错，链自动降级且前端显示"已降级到 X" |
| **V1-9** 文档与验收演练 | README、部署指南、搜索与数据源配置指南（发布版）、真实事件全流程演示 | 请一位非开发者按 README 走通并计时 |

### 3.4 V1 与样张规格的差异（需要注意的衔接点）

- 样张里的传播图表是**示意数据**，V1 必须换成真实口径三张图（票 11 决议 3）。样张的示意标注方式**仅限样张**，不进正式产品。
- 样张的 KPI 卡有"热度峰值"，V1 **不出这张卡**——热度数据要等 V1.5 的热榜快照库才能真算出来。
- 样张的历史对照卡是手工调研的，V1 由 `history_insight` 用搜索 API 时间回溯自动产出，质量会有波动，需在验收时人工抽检。

## 4. V1.5 · 数据纵深与交付完善

### 4.1 范围（票 13）

历史数据层完整（公开数据集一键导入 + 热榜快照定时积累入 SQLite）→ 历史对照板块升级为真实数据驱动；PDF 导出（图表转静态）；报告 IR 稳定化；演示站部署。

### 4.2 验收标准（票 13）

- [ ] 新事件专报可叠加热榜真实热度数据（仅当事件落在热榜采集覆盖期内）。
- [ ] **已覆盖事件**的历史对照优先来自本地库检索并标注"本地库命中"；未覆盖事件正常回退搜索回溯（审查修订：本地库是辅助层——热榜快照只有榜单标题、数据集话题有限，不承诺任意事件都能本地命中）。
- [ ] PDF 与 HTML 内容一致且引用保留。

### 4.3 开发顺序

| 步骤 | 内容 | 说明 |
|---|---|---|
| **V15-1** 公开数据集导入 | `scripts/import_dataset.py`：微博热搜历史小时级数据、话题舆情数据集等一键下载入库 | 解决"装好就有历史可查"（票 07 第 1 层） |

## 5. V2 · 远期增强

范围（票 13）：

- **用户自带 Cookie 的深度评论可选插件**：默认关闭、独立开关、明确风险声明、不作为任何核心功能的依赖（合规边界见 SPEC §6.3）。
- **本地 NLI 核验增强**：在 LLM 交叉核验之外增加本地 NLI 模型做二次判定，提升核验一致性并降低成本。
- **多语言 / 境外信源扩展**：英文与其他语种信源接入，用于国际关注度高的事件。

（舆情监测与预警平台化仍在本方案包范围之外，属另起 effort 的愿景。）

## 6. 关键风险与对策

| # | 风险 | 触发场景 | 对策 | 归属阶段 |
|---|---|---|---|---|
| R1 | **免费 API 额度/限速触顶** | 三 agent 并发触发 LangSearch 1 QPS 限速（429）；千帆按天发放约 50 次当日耗尽；开发期反复调试烧额度 | ①配额感知 + provider 级令牌桶限速（架构 §7.2）；②预算表硬限单次分析的搜索次数（架构 §8.4：standard ≤40 次）；③开发期用 `tests/fixtures/` 固定搜索结果跑回归，不打真实 API；④质量优先链用按次计费的智谱（0.01-0.05 元/次，调试成本可忽略） | M0 起 |
| R2 | **涉敏事件触发模型安全拦截** | 舆情事件天然涉敏；BettaFish 已实证"敏感词导致整个流程跑不通" | 失败先分类（transient/quota/policy_block/privacy_block/unsupported，SPEC §6.5）：policy/privacy 类**不做跨模型规避式重试**，至多一次中性化改写，仍拒则该板块降级为"仅呈现证据"，多数节点被拦时进入稳定的"因政策终止"态；明确不学 BettaFish 的"已通过伦理审查"话术 hack。**竞赛现场预演三种故障**：断网（离线 fixture 全流程）、全模型拒答（预生成报告兜底）、限流；现场演示事件用预审白名单 | V1 |
| R3 | **搜索质量不足导致证据太少** | 冷门事件、时效过久的事件 | ①检索词工程 skill（分平台语言风格、反书面语）；②多 provider 能力互补（需要时间过滤时优先选支持 freshness 的）；③证据不足时**明确产出"证据不足"报告**并在局限性声明说明，绝不靠模型补足 | V1 |
| R4 | **LLM 结构化输出不稳定** | 国产端点对 JSON mode 支持参差 | JSON mode 优先 → schema 嵌提示词 + pydantic 校验 → 四类失败分类重试（解析失败/结构失败/内容过稀/安全拦截）→ 最优候选兜底（学 BettaFish ReportEngine 唯一做得很细的地方） | M0 起 |
| R5 | **单次分析耗时过长** | 三 agent × 多轮 + 报告生成 | ①预算器三级限额；②三 agent 并行 + 无依赖章节并发生成；③速览版先出、完整版后补；④用户可随时"停止并出报告" | V1 |
| R6 | **大陆网络访问不通** | Jina Reader 大陆直连不通（2026-04 实测）；Tavily 偶有波动 | 抓取链必须内置 httpx + trafilatura 本地兜底；文档明确标注哪些服务需要代理；默认链不放需代理的服务在 P0 | M0 |
| R7 | **入门开发者被工程复杂度卡住** | 一次性搭完整架构 | 竖切开发（M0 九步每步可运行）；`import-linter` 守边界防止越写越乱；单文件超 600 行强制拆 | 全程 |
| R8 | **报告出现事实错误，可信度崩塌** | LLM 误读原文、引用错配 | ①渲染层硬拦截（无引用不进正文、`illustrative` 不进正文）；②每阶段结束做真实事件人工抽检（随机 10 条 claim 逐条回原文核对）；③把抽检结果记入项目文档，作为质量基线 | 每阶段末 |
| R9 | **依赖第三方公共实例不稳定** | DailyHotApi 公共实例、newsnow 公共实例可能停服（BettaFish 就依赖后者） | 自部署 DailyHotApi（MIT，Docker 一条命令）或配置多实例轮询；热榜层缺失时历史洞察自动降级到搜索回溯 | V1.5 |
| R10 | **开源许可冲突** | 参考了 GPL 项目（BettaFish GPL-2.0、TrendRadar GPL-3.0） | 独立实现，不复制其源码，只借鉴设计思路；不内置"非商业学习使用"许可的组件（MediaCrawler）；发布前做一次依赖许可扫描 | V1 收尾 |
| R11 | **演示站被跑爆或被滥用** | 公开演示站 + 自己的 API key | 只读演示模式：并发上限、单次预算上限、每 IP 每日次数上限、预置若干示例报告直接展示；**禁用配置写接口、演示 key 与个人 key 隔离**（架构 §7.4）；内容治理（TTL / takedown，SPEC §6.6） | V1.5 |
| R12 | **热榜/数据集含个人信息或许可不明** | 数据集里可能含用户昵称等；部分数据集无明确许可（如 weibo_senti_100k） | 导入时做字段白名单，只保留标题/热度/时间/URL 等非个人字段；**数据资产登记表逐源登记许可，许可不明的不做一键导入、不随项目分发**（04 §8.1） | V1.5 |
| R13 | **不受信网页的安全风险** | 恶意页面诱导 SSRF（抓内网/云元数据）、网页提示词注入、快照 XSS | 架构 §7.4 五条防线（协议与内网地址阻断＋重定向复检、大小与类型上限、不受信内容显式定界、快照清洗＋sandbox、演示站禁写接口）；M0-4 起生效并配负向测试 | M0 起 |
