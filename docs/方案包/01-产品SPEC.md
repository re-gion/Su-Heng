## 1. 产品定位与目标用户

### 1.1 一句话定位

**输入一个舆情事件名，自动产出一份"每个重要结论都能点回原文"的结构化舆情专报。**

### 1.2 目标用户

主用户是 **C 端个人用户**：想快速、全面地搞清楚一件舆情事件的真实经过与发酵过程，而不是想监测自己品牌的企业公关。具体画像分三类：

| 用户类型 | 典型场景 | 他现在的替代方案 | 替代方案的痛点 |
|---|---|---|---|
| 关心热点的普通人 | "海天酱油双标到底是怎么回事，网上说的哪些是真的" | 刷微博/知乎、问 AI | 信息碎片、真假混杂、AI 会编 |
| 学生 / 研究者 / 自媒体作者 | 写论文、写稿、做视频要梳理事件脉络与各方观点 | Deep Research 类产品 | 自由文本综述、引用需逐条人工核验、无时间线结构 |
| 技术爱好者 / 开源用户 | 想在本地跑一套舆情分析系统 | BettaFish（4.2 万 star） | 部署门槛高、报告无来源可溯、幻觉高、跑三小时会卡死（票 06 / issues 实测） |

### 1.3 产品形态

- **开源自部署 + 演示站**，不做在线 SaaS 运营（规划地图已定）。
- 部署形态：一个 Python 进程（FastAPI 同时托管后端 API 与前端构建产物）+ 一个 SQLite 文件，零外部中间件（票 12）。
- 用户自带 key（BYOK）：LLM key 必填至少一个，搜索链默认可用免费档。

### 1.4 与 B 端舆情产品的关系

原 PRD 已判断正确并保留：商业舆情服务（蜜度、拓尔思、人民在线等）面向政企、竞争饱和、依赖长期私有数据积累。本项目**不打监测预警赛道**，只做"把一件已经发生的事讲清楚、讲得可核验"。舆情监测与预警平台化在本方案包范围之外（属日后另起的 effort）。

## 2. 差异化定位

### 2.1 第一卖点：可核验性（票 08）

> **核心主张：可核验的舆情专报——每个重要结论都能点回原文。**

这不是一句宣传语，而是四件必须落在架构里的事（详见 §5）：

1. **claim 级结构化引用**：每个论断绑定具体证据 ID，不是文末列一堆链接。
2. **自动核验**：低成本异构模型逐条比对 claim 与其引用原文，输出支持/部分支持/不支持。
3. **四级核验标记**：已证实 / 待核验 / 争议 / 已证伪（票 10 Amendment）。
4. **证据留存**：搜索到的原文快照本地存档，事后可离线回看，不怕链接失效。

**为什么这一点站得住**（票 06 调研）：

- Deep Research 类产品（OpenAI / Perplexity / Gemini / Kimi / 秘塔）的公认缺陷是"错引真实来源"式幻觉——引用的链接是真的，但那句话原文里没有；多篇横评一致结论是"用户必须逐条点开核验"。
- BettaFish 的 GitHub issues 里用户直接提了两条：「生成的报告能否获取到信息来源」「幻觉率太高且带有负面批判性倾向」。
- 学术侧有现成方法论可对齐：ALCE 基准（arXiv:2305.14627）把引用质量拆成 citation recall / precision 并用 NLI 自动判定，其结果显示当时最佳模型在 ELI5 上仍有 **50% 的句子缺乏完整引用支持**——说明这件事既没被解决，又可量化。

### 2.2 三个支撑差异点（票 08，按优先级）

**支撑点 1 · 结构化专报三件套：事件时间线 + 传播分析 + 历史相似事件对照**

Deep Research 给的是自由文本综述，给不了信息架构。其中"历史对照"是 BettaFish 与 Deep Research 都没有的空档（票 01 §8.2 第 8 条明确指出 BettaFish 的 InsightEngine 只查"库里有什么"，没有事件对比、周期分析、相似案例检索）。

**支撑点 2 · 零门槛 C 端体验**

对比 BettaFish 的"多 API key + 强制 MySQL + Docker + 跑三小时"（票 06 issues 实测），本项目：单进程、单 SQLite、免费搜索链默认可用、输入事件名一键出报告。这是在收割一个已被 4.2 万 star 验证过、但被部署门槛挡在门外的用户群。

**支撑点 3 · 可讲的技术叙事**

- **异构分工 + 证据仲裁降幻觉**：学术反面证据显示同构多 agent 辩论**不能稳定优于**单 agent 基线（arXiv:2502.08788），但**模型异构能显著改善**；且弱模型在辩论中有严重从众效应（arXiv:2606.10296）。因此本项目不做"同一个模型自我辩论"，而是不同底模 + 不同信源分工 + 证据仲裁（票 06 / 09）。
- **合规优先的轻数据层**：默认只碰公开数据与公开榜单，逐源登记许可与风险（§6.1）后随开源产品分发；对比 BettaFish 依赖灰色爬虫集群（票 04 / 07）。

### 2.3 与两类主要参照物的逐项对比

| 维度 | BettaFish（微舆） | Deep Research 类 | 本项目 |
|---|---|---|---|
| 结论可溯源 | 报告不带引用（用户 issue 实证） | 文末引用列表，句子级归属弱、错引常见 | **claim 级绑定 evidence_id，无引用不进正文** |
| 核验状态 | 无 | 无 | **四级徽章 + 独立信源数 + 最高信源等级** |
| 证据留存 | 无 | 无（链接失效即断） | **原文快照本地存档，可离线核查** |
| 信息架构 | 章节式长报告（IR→交互式 HTML，做得很好） | 自由文本综述 | **十板块结构化专报 + 速览/完整双版** |
| 时间线 | 无专门结构 | 无 | **有，含转折点标记** |
| 历史对照 | 无 | 一般不做 | **有（三层数据层支撑）** |
| 社媒民意深度 | **强**（自建爬虫 7 平台帖子+评论） | 弱（抓不到登录态内容） | 中（公开数据 + 热榜；深度评论为 V2 可选插件）——**这是取舍不是缺陷** |
| 传播图表数据来源 | LLM 转写产生，只校验结构不校验真伪（票 01 §5.3） | 一般不出图 | **强制来自证据库真实统计，算不出来就不画** |
| 幻觉控制 | 提示词 + 主持人纠错 | 模型自身能力 | **证据先行 + 结构化绑定 + 异构交叉核验 + 渲染层硬拦截** |
| 中断恢复 | 无（用户 issue：跑三小时睡死，没法 rerun） | 不适用 | **每轮 state 落盘，可从最近轮次续跑** |
| 部署 | 多 key + MySQL + Docker | 云服务 | **单进程 + SQLite** |
| 合规 | 灰色爬虫、prompt 里写"已通过伦理审查"话术 | 不适用 | **架构级合规：默认不碰登录态数据** |

### 2.4 一句话区隔与竞赛叙事线

> BettaFish 是"重数据依赖、结论不可溯源"的舆情分析系统；本项目是"轻数据、合规优先、每句话可核验"的 C 端舆情研究工具。

竞赛叙事三段式（票 08）：
1. 一个 4.2 万 star 的开源项目 + 它的 442 条 issues，证明了需求真实存在、痛点非常明确；
2. 本项目以"可核验性"为灵魂重新设计整条链路，而不是把它的功能再抄一遍；
3. 差异化可被量化验收：引用覆盖率、核验通过率、争议项显性率都能当场测给评委看。

### 2.5 明确不做（避免被大厂顺手覆盖）

- 不做"搜索 + 总结"式的通用综述（正面打 Deep Research 必输）。
- 不做舆情走向预测：学术上 LLM 社会模拟准确率仅 60%+ 且有系统性偏差（票 06），且预测本身不可核验，与第一卖点冲突。V1 只做"已发生传播的结构化描述 + 历史相似事件对照"。
- 不做新闻分发/资讯流：纯 C 端新闻时间线产品「后续」App 死于新闻资质与监管而非需求（票 06）。本项目定位是**个人研究工具**，输出永远附原文链接，不替代原始媒体。

## 3. 功能规格：完整用户旅程

### 3.1 旅程总览

```
[1] 输入事件           [2] 分析过程可视化              [3] 专报输出
  ┌──────────┐      ┌──────────────────────┐      ┌──────────────┐
  │ 事件名    │      │ 三 agent 并行工作面板   │      │ 速览版（默认）│
  │ + 可选时间 │ ──▶ │ 论坛讨论流             │ ──▶ │ 一键展开完整版 │
  │ 范围/补充  │      │ 证据入库计数            │      │ 引用可点可回溯 │
  └──────────┘      │ 主持人评审 / 轮次        │      │ 导出 HTML/PDF │
                     └──────────────────────┘      └──────────────┘
                       全程 SSE 实时推送，可中断、可续跑
```

### 3.2 第一步：输入事件

**主输入**：一个事件名或一句话描述（如"海天酱油添加剂双标风波"）。

**可选输入**（默认全部留空也能跑）：
- 时间范围：不填则由系统按事件热度自动判断（搜索时用 `freshness` 参数逐级放宽）。
- 补充说明：用户已知的关键信息或特别关注的问题（会注入各 agent 的初始任务描述）。
- 分析深度：快速（单 agent，约 3-5 分钟）/ 标准（三 agent + 一轮论坛）/ 深度（三 agent + 最多 3 轮论坛）。对应不同的 token 预算与轮数上限。

**创建任务后立即返回 task_id 并跳转到过程页**，不阻塞等待。

### 3.3 第二步：分析过程可视化（产品亮点，不只是 loading 动画）

这一屏本身就是差异化体验：用户能看见"这份报告是怎么被查出来的"。四个区域：

| 区域 | 内容 | 数据来源（SSE 事件） |
|---|---|---|
| Agent 工作面板 ×3 | 每个 agent 当前阶段（计划/搜索/总结/反思）、本轮搜索词、命中条数、内循环第几轮、终止判定理由 | `agent.status`、`loop.round` |
| 论坛讨论流 | 各 agent 的结构化发言、主持人评审（缺口清单/共同盲点/矛盾清单）、下一轮引导 | `forum.message`、`host.review` |
| 证据流 | 新入库证据卡片（标题、来源、信源等级徽章、发布时间），实时累加计数 | `evidence.added` |
| 核验进度 | claim 逐条核验结果，四级徽章实时点亮 | `verify.progress` |

**关键交互**：
- 用户可随时"暂停"和"停止并出报告"（不必等跑完，用已有证据出一份带局限性声明的报告）。停止的运行时语义是"先封存进度、拒绝迟到写入、再取消未完成 agent"（架构 §4.5），保证报告与数据库一致。
- 页面刷新/断线重连后，通过 `?since_seq=` 补发历史事件，不丢进度。
- 任务失败或进程崩溃后，任务列表页提供"续跑"按钮，从最近一个完成的轮次继续（票 09）。

### 3.4 第三步：专报输出

- 生成完成后自动跳转到报告页，默认展示**速览版**（约 2 屏：执行摘要 + 关键事实核查表 + 研判结论），顶部一键"展开完整版"（票 11 决议 5）。
- 报告是**自包含单文件 HTML**：图表库、字体、原文关键句、内容哈希与外部 URL 全部内联，离线可打开、可转发、可归档（学 BettaFish 最强的 ReportEngine 形态，票 01 §5）。**完整原文快照不内嵌**（体积与第三方脚本安全都不可控，审查修订）：快照在部署机的报告页可点开查看；需要连快照一起交给别人时，用 V1.5 的"证据包 ZIP 导出"（报告 + 清洗后的只读快照 + 清单文件，相对路径打包）。
- PDF 导出：V1.5 交付，图表转静态，内容与引用与 HTML 一致（票 13）。
- 报告默认长期保存在本地 SQLite + 文件系统，任务列表页可随时重看；删除任务会联动清理其证据、快照与报告文件（§6.6）。

## 4. 专报内容规格（十板块）

> 本节是专报的权威规格，来源于样张 `prototypes/report-mockup-v1.html` 与其设计说明，并已并入票 11 的五项评审决议。
> 报告由**报告 Agent 产出结构化 IR（JSON），渲染层确定性渲染**——LLM 不直接写 HTML（票 01 §5.2 证明这是正确形状）。

### 4.0 板块总表

| # | 板块 | 产品意图 | 速览版是否包含 | 硬性约束 |
|---|---|---|---|---|
| 00 | 报告头 + KPI 概览 | 3 秒建立"这是什么报告、可信度如何" | ✅ | KPI 必须标 `实计`；算不出的不展示（不画示意） |
| 01 | 执行摘要 | 不读全文也能拿走结论 | ✅ | 句内带引用标；**禁止出现编辑判断内容** |
| 02 | 事件时间线 | 还原"事情怎么一步步走到这一步" | ❌ | 每个节点必须绑定 evidence_id；转折点显式标记 |
| 03 | **关键事实核查表** | 产品灵魂 | ✅ | 每条 claim 必须有四级徽章 + ≥1 条引用卡片 |
| 04 | 传播分析 | 让"热度"可视化且不撒谎 | ❌ | 图表数据只能来自证据库真实统计或热榜快照 |
| 05 | 情感与观点 + 低声量问题 | 呈现分歧而非制造共识 | ❌ | 编辑判断内容必须视觉隔离 + 打标签 |
| 06 | 历史对照 | 提供纵深 | ❌ | 每张对照卡必须是真实事件且带来源 |
| 07 | 研判与建议（C 端向） | 教读者怎么判断 | ✅ | 编辑判断内容必须打标签并计入局限性声明 |
| 08 | 局限性声明 | 可信度的反向证明 | ✅ | **必出，不允许为空**；强制放行的未解决项必须在此列出 |
| 09 | 证据清单附录 | 全部引用可回溯 | ❌ | 编号、来源、信源等级、日期、URL、快照链接 |

### 4.1 板块 00 · 报告头 + KPI 概览

**字段**：事件名、副标题（一句话定性）、事件时间范围、追踪截止时间、报告生成时间、报告编号、所用模型与搜索源摘要。

**KPI 卡**（4 张，全部必须可由本次分析数据算出）：
- 引用信源数（证据库去重域名数）
- 核验通过率（见 §5.6 口径）
- 证据总条数 / 其中官方级条数
- 覆盖时间跨度（最早证据发布时间 → 最新）

**"示意 / 实计"标记制度**（票 11 决议 3 的正式版口径）：
- IR 中每个数值型块必须带 `data_basis` 字段，取值 `computed`（由证据库/热榜真实算出）/ `external`（用户显式导入的外部数据）/ `illustrative`（示意）。
- **渲染层硬规则：`illustrative` 一律拒绝进入正式专报**（与"无引用 claim 拒入正文"是同一条防线）。算不出来的 KPI 直接不展示该卡，算不出来的图表降级为文字说明并在局限性声明里记一条。
- `external` 允许展示，但必须显示"外部数据"标签与数据来源说明。
- `illustrative` 能力保留在 IR 与渲染器里（样张演示、模板预览用），正式报告链路默认关闭。

### 4.2 板块 01 · 执行摘要

- 结构：导语（lede，2-3 句）+ **WHAT / WHY / SO WHAT** 三栏。
- 每一句结论性陈述句内带引用标 `[E##]`。
- **硬规则：执行摘要中不得出现任何 `is_editorial=true` 的内容**（票 11 决议 4）。

### 4.3 板块 02 · 事件时间线

- 节点字段：日期（精确到日，能到时则到时）、事件描述、来源编号、可选引文块、`is_turning_point` 与转折类型标签（如"第一次转折""舆情峰值""代价兑现""制度回响"）。
- 每个节点必须绑定至少一个 evidence_id；日期以证据中的发布时间或原文明示时间为准，二者冲突时以原文明示时间为准并在节点上标注。
- 时间线方法可参考 CHRONOS（阿里通义，NAACL 2025，已开源，arXiv:2501.00888）的"迭代自我提问 + RAG"思路（票 06）——**V1 不引入其代码，只借鉴提问式补全的提示词策略**。

### 4.4 板块 03 · 关键事实核查表（核心板块）

**条目写法的硬规则**（样张设计决策 2 + 审查 P0 修复"徽章的判定对象"）：

1. **徽章永远作用于条目正文那句话**（被核验陈述）。条目分两种（`statement_kind`）：
   - **fact 条目**：正文 = 经核验的中性可核验陈述；网络流传版本单列在条目下方灰字区（仅展示、不核验）。
     反例：条目写"海天在国外卖零添加、在国内卖科技与狠活"然后打绿色"已证实"徽章 → 读者会误读成"这条指控是真的"。
     正例：条目写"海天同一品牌在中日两地销售的部分产品配料表存在差异"。
   - **rumor 条目（辟谣）**：正文 = 流传说法本身（显式标"流传说法"），打"已证伪"深红标直接否定它；核验结论行给出经证据支持的真实情况（`correction_text`）。
     这样"已证伪"永远不会出现在一句真话旁边——核验器核验的、徽章否定的，都是屏幕上完整展示的那句话。
2. 每条 claim 展开后必须显示**核验结论行**：核验结论（支持/部分支持/不支持/信源矛盾）、独立信源数（按原始采编主体归并）、最高信源等级；rumor 条目附"真实情况"一行。
3. 每条 claim 至少一张**引用卡片**。

**四级核验徽章语义**（票 10 + Amendment，权威定义）：

| 徽章 | 判定规则 | 视觉 | 语义 |
|---|---|---|---|
| **已证实** | ≥2 个独立信源支持（独立性按**原始采编主体**归并计数——同集团多站、一稿多站转载不重复计）；**或**裁判性官方单源支持（政府通报/监管公告/标准文本/生效判决，且非当事方；卡片必须注明"单源·官方"） | 绿 | 这件事成立 |
| **待核验** | 单个非官方级信源支持，或核验结论为"部分支持" | 黄 | 目前只有这一处说法/说法不完整 |
| **争议** | 不同信源之间相互矛盾 | 橙红 | 各方说法打架，尚无定论 |
| **已证伪** | 证据充分否定条目正文那句话（rumor 条目：正文即流传说法） | 深红 | 这个说法不成立（但因传播广泛仍保留展示） |

> 注意与修订前的差别：修订前"核验不支持但传播广泛"被塞进"争议"，导致读者误以为"还没定论"。四级制把它独立为"已证伪"（票 11 决议 1）。

**当事方声明规则（审查 P0 修复）**：企业/机构对**自身争议事项**的声明属于当事方陈述（`source_role='party'`），即使其信源等级为 L1，也**不适用官方单源规则**——它只能证实"该方作出过此声明"这类归属性 claim，不能证实声明内容为真；声明内容是否属实需要独立信源或裁判性权威来源支持。同一份声明被多家门户转载，按一个信源计。

**引用卡片字段**（除注明可缺省者外必填，缺失不可渲染）：

| 字段 | 说明 |
|---|---|
| 来源名称 | 媒体/机构名，如"国家标准信息公共服务平台""界面新闻" |
| 信源等级 | 五级色标，见 §5.5 |
| 发布日期 | 来自证据库 `published_at`，无法取得时显示"日期未知"并降低核验权重 |
| 原文关键句 | 从证据正文中摘出的、直接支撑该 claim 的句子 |
| 引述类型标签 | **原文引述**（逐字，且必须在已抓取的原文全文中精确匹配、记录偏移，校验不过自动降级为转述）/ **要点转述** / **搜索摘要**（证据只有搜索 API 摘要、原文未抓到时的唯一合法标签）——这是本产品与"AI 幻觉式引用"的分界线 |
| 原文 URL | 可点击跳转 |
| 快照链接 | 已抓到原文时提供本地存档链接（部署机可查看；连快照一起转发用 V1.5 证据包导出）；未抓到原文时此处显示"原文未取得"标注（可缺省场景） |

### 4.5 板块 04 · 传播分析

**正式版数据口径**（票 11 决议 3，替换样张的示意数据）：

| 图表 | 数据来源 | 算法 |
|---|---|---|
| 报道数量时间分布 | 证据库 `evidence.published_at` | 按日/周分桶计数 |
| 信源类型分布 | 证据库 `evidence.source_tier` | 五级分类计数 |
| 平台/视角分布 | 证据库 `source_domain` 归类 | 官媒/市场化媒体/门户/行业自媒体/境外 分组计数 |
| 热度曲线（V1.5 起） | 本地热榜快照库 | 仅当事件发生在热榜采集覆盖期内才出图 |

**硬规则**：以上任一图表数据不足（如证据数 < 8 条、时间跨度 < 2 天）时不出图，改为文字说明 + 局限性声明记一条。**不画示意图。**

配套内容：热点关键词（从证据标题与正文抽取的高频词，标注统计口径与样本量）。

### 4.6 板块 05 · 情感与观点 + "声量低但值得注意的问题"

- **代表性观点**：每条含观点摘要、立场标签（企业/协会/专家/媒体评论/网民）、来源引用。观点必须来自证据原文，不能由模型概括"网民普遍认为……"这类无出处陈述。
- **"声量低但值得注意的问题"**：回应原 PRD"声量低、冷门但严重的问题"的要求。这是专报里最容易出彩、也最容易越界的部分，因此适用编辑判断隔离规则（§4.10）。
- 情感占比图：只有在有可量化情感样本（如公开数据集匹配、热榜情绪标签）时才出；纯靠 LLM 感觉打出的百分比**不允许出图**。

### 4.7 板块 06 · 历史对照

- 每张对照卡：历史事件名、时间、一句话经过、结局、与本事件的相似点与关键差异，**必须带来源引用**。
- 5 维对比表：事件性质、爆发路径、企业/机构应对、监管介入程度、最终结局。
- 数据来源分期（票 07 三层轻数据层）：
  - **V1**：搜索 API 时间过滤按需回溯（用 `oneYear` 等参数查历史报道）。
  - **V1.5**：叠加本地库**辅助**检索（公开数据集导入 + 热榜快照积累）。**边界诚实（审查 P1 修复）**：本地库覆盖面天然有限（热榜快照只有榜单标题与热度、数据集话题有限），历史对照的主数据源始终是搜索回溯；本地库命中时优先采用并标注"本地库命中"，未命中不算失败。

### 4.8 板块 07 · 研判与建议（C 端向）

**定位边界**：教读者**怎么判断**，不教企业怎么公关。这是 C 端定位在内容层的直接体现，也是与 B 端舆情报告最明显的差别。

典型条目形态（取自样张，作为写作模板）：
- 目前最可靠的结论是什么（以及它为什么可靠）
- 遇到这类爆料先问哪三个问题
- 怎么读企业声明（哪些话是承诺，哪些是措辞）
- 作为消费者/读者，实际该关注什么
- 什么时候该"再等等"（信息尚未充分时的判断建议）

本板块整体属于编辑判断，适用 §4.10 规则。

### 4.9 板块 08 · 局限性声明（必出）

**这是可信度的反向证明，不允许为空。** 按类型标签分组，至少覆盖以下来源：

| 来源 | 触发条件 |
|---|---|
| 一手材料缺失 | 关键 claim 无官方级信源 |
| 核心缺口 | 大 Loop 强制放行时主持人的 `unresolved_critical` 清单（票 09） |
| 数值为二手 | 关键数字来自媒体转述而非原始发布方 |
| 图表未出 | 因数据不足而降级为文字的图表 |
| 官方缺位 | 事件相关方或监管方未公开表态 |
| 时效风险 | 事件仍在进展中，报告有截止时间 |
| 主观成分 | 本报告包含 N 条编辑判断内容，位于第 05/07 节 |
| 核验强度降级 | 用户只配了一个 LLM，核验模型与生成模型同源（见 §5.4 注） |
| 搜索链降级 | 某些 provider 配额耗尽或失败，实际检索广度受限 |

局限性声明的条目由系统**自动生成**（来自任务运行时的真实状态），不是让 LLM 自由发挥写几条谦虚话。

### 4.10 编辑判断隔离规则（票 11 决议 4，硬规则）

"编辑判断"= LLM 的推理产物，不是可直接核验的事实（如"这件事的深层原因可能是……""值得注意但没人讨论的一点是……"）。

**接受它进入专报，但必须同时满足四条：**

1. **视觉隔离**：独立样式块（浅底 + 左侧竖线），与事实性内容明显区分。
2. **显式标签**：块内必须显示「编辑判断」标签。
3. **不得进入执行摘要**（板块 01），也不得出现在关键事实核查表（板块 03）。
4. **计入局限性声明**：报告自动统计编辑判断条目数并在板块 08 声明。

**补充规则（本 SPEC 新增，用于消解票 10 与票 11 之间的规则边界）**：编辑判断内容**不参与引用覆盖率指标统计**（它本来就不是 claim），但**必须在 IR 中声明其推理所依据的 evidence_ids**（弱绑定）——即"我这个判断是从哪几条证据推出来的"。完全无证据支撑的自由发挥仍然拒绝进入专报。

### 4.11 速览版 / 完整版双版渲染（票 11 决议 5）

- 报告 IR 中每个块带 `in_brief: true|false` 标志。
- **速览版**（默认展示，约 2 屏）：板块 00 + 01 + 03（仅"已证实"和"已证伪"两级 claim）+ 07 + 08 摘要。
- **完整版**：十板块全量，一键展开，URL 带 `?view=full` 可直接分享完整版。
- 两版共用同一份 IR 与同一个 HTML 文件，靠前端切换，不重复生成。

### 4.12 视觉标准（票 11 已定稿，直接执行）

**新闻编辑室风格，不是 SaaS Dashboard。**

- 底色暖灰纸感 `#f5f4f1`，卡片纯白，1px 冷灰描边；圆角仅 2px、无阴影、无渐变按钮、无紫色。
- 主色只有一个墨蓝 `#1c3f63`。**语义色（绿/黄/橙红/深红）只用于核验徽章、情感图、转折点标记，绝不用于装饰。**
- 字体三分工：衬线标题（思源宋体族）+ 无衬线正文 + 等宽数字与 URL。
- 正文行高 1.85、栏宽 940px；章节用 2px 墨色下划线切分。
- 交互：左侧固定目录 + 滚动高亮、核验徽章按级筛选、claim 点击展开、引用标悬浮预览 + 点击跳转高亮、打印样式（隐藏导航、自动展开引用）。

**遗留技术备忘（进入实现期）**：图表库必须内联保证离线可用；中文衬线字体需子集化自带（Windows 上系统字体会降级到 SimSun，观感明显变弱）。

## 5. 数据真实性机制（产品的生命线）

> 设计原则：**机制嵌进架构，而不是靠提示词祈祷。** 提示词只是三层防线中的第一层。

### 5.1 证据先行的数据流（票 10 第 1 条）

```
搜索/抓取 ──▶ 证据库（先落库，含原文快照）──▶ agent 只能引用已入库的 evidence_id
                                              ▲
                                              └── 引用一个不存在的 ID = schema 校验失败 = 直接重试
```

**这一条是整套机制的地基**：agent 无法"编造来源"，因为它能引用的东西必须先真实存在于库里、有 URL、有快照、可回看。这与"先让 LLM 写完再去检查它有没有编"是根本不同的两种做法。

证据有**抓取状态机**（审查 P0 修复）：`discovered`（仅有搜索结果元数据 + 摘要）→ `fetched`（已抓原文：正文抽取 + 快照 + sha256）或 `fetch_failed`。仅 `discovered` 的证据也可以被引用，但其引述类型只能标"搜索摘要"（§4.4），永远不能冒充"原文引述"。

证据入库字段（详见架构文档 §6 表设计）：`evidence_id / URL / 标题 / 发布时间 / 来源域名 / 原始采编主体 / 来源角色 / 信源等级 / 抓取状态 / 正文抽取 / 原文快照路径 / 检索用的 query / 来自哪个 provider`。

### 5.2 claim 的结构化（票 10 第 2 条）

```json
{
  "claim_id": "C07",
  "text": "海天味业是酱油国家标准 GB/T 18186 的第一起草单位",
  "rumor_text": "国标是海天自己定的",
  "evidence_ids": ["E09"],
  "quotes": [{"evidence_id": "E09", "text": "起草单位：佛山市海天调味食品股份有限公司……", "quote_type": "verbatim"}],
  "agent": "fact_investigator",
  "round": 1,
  "section": "fact_check"
}
```

由 JSON schema 约束产出（优先用模型的 JSON mode / structured output，兼容性不足时回退到"schema 嵌提示词 + pydantic 校验 + 一次重试"）。

### 5.3 LLM 交叉核验（票 10 第 3 条）

**核验器 = 与生成 agent 异构的低成本模型**（如生成用 Kimi/Gemini，核验用 DeepSeek）。

流程：
```
对每条 claim：
  取出它引用的每条证据的原文片段（±上下文若干字）
  ──▶ 核验器：这段原文是否支持这条 claim？
      输出 {结论: 支持|部分支持|不支持, 理由: "...", 引用了原文哪一句}
  ──▶ 汇总所有证据的核验结果 + 独立信源数 + 最高信源等级
  ──▶ 映射到四级徽章（规则见 §4.4）
```

**多源互证**：同一 claim 被 ≥2 个**独立信源**的证据一致支持时，判"已证实"——独立性按**原始采编主体**（`publisher_entity`）归并计数：同一媒体的转载稿、同一集团的多个站点、同一通讯稿被多家门户转发，都只算一个信源（归并规则可配置，无法识别采编主体时退化为按可注册域名）。摘要级证据（原文未抓到）互证同样可判"已证实"（用户确认的宽松口径），但引用卡片会注明"原文未取得"、引述类型标"搜索摘要"。核验器核验的对象永远是 claim 正文那句话（§4.4 规则 1）；其完整提示词与金样例见 05-核心契约。

> **注（本 SPEC 补充，用于消解票 09/10 与票 13"单一 LLM 也能跑"之间的张力）**：当用户只配置了一个 LLM 时，系统不阻止运行，但会：(a) 用同一模型做核验；(b) 在报告局限性声明中自动加一条"核验模型与生成模型同源，交叉核验强度降低"；(c) 在设置页提示配置第二个模型可提升核验可信度。默认配置模板中，`verifier` 角色预填一个免费/低价的异构模型建议值。

### 5.4 "不知道不说、不编造"的三层落实（票 10 第 5 条）

| 层 | 做法 |
|---|---|
| **提示词层** | 各 agent 系统提示词明确：只允许基于已入库证据陈述；不确定的必须写进"缺口"字段而不是编出来；禁止使用"据了解""有网友表示"等无出处措辞 |
| **机制层** | 无 evidence_id 的重要 claim **在渲染层被拒绝进入专报正文**——不是警告，是丢弃并记入日志 |
| **呈现层** | 所有未解决项进入局限性声明板块，承接大 Loop 强制放行时主持人的未解决清单 |

### 5.5 信源五级分类（票 11 已定稿）

| 等级 | 名称 | 例子 | 核验权重（初版） |
|---|---|---|---|
| L1 | 官方 / 标准文本 | 政府通报、国家标准数据库、监管公告、企业官方声明原文 | 1.0（**单源可判"已证实"**） |
| L2 | 主流媒体 | 人民日报、新华社、财新、界面、每经、澎湃等有采编资质媒体 | 0.8 |
| L3 | 门户 / 聚合 | 新浪、网易、凤凰、观察者网等转载与聚合平台 | 0.6 |
| L4 | 行业 / 自媒体 | 行业垂直站、财富号、虎嗅等 | 0.4 |
| L5 | 百科 / 待交叉 | 维基百科、百度百科等需交叉验证的来源 | 0.2 |

实现为可配置的域名分级表（`source_tiers.yaml`），用户可增补。未识别域名默认归 L4 并在引用卡片标注"未分级来源"。

**信源等级 ≠ 裁判资格**（审查 P0 修复）：等级衡量"来源本身的权威性"，与证据的**来源角色**（`source_role`：裁判性权威 / 当事方 / 独立媒体 / 转载）是两个维度。企业官方声明原文属 L1，但对自身争议是当事方——不适用官方单源判"已证实"的规则（见 §4.4 当事方声明规则）。官方单源规则仅适用于对该命题具有裁判性地位的权威来源（监管结论、生效判决、标准文本、政府通报）。

### 5.6 可量化验收指标（票 10 第 7 条 + 11 决议 2 的口径要求）

三个指标随报告一起展示，也是路线图的验收依据：

1. **引用覆盖率** = 进入专报正文的重要 claim 中，绑定了 ≥1 个 evidence_id 的比例。目标值：**100%**（渲染层会拦截，未达标即是 bug）。
   > **防"过滤后恒等式"（审查 P1 修复）**：这个 100% 是渲染层拦截的结果，不证明调查完整。报告指标区必须**同时展示**：候选重要 claim 总数、被渲染层拦截的条数及原因分布、被模型降级为"非重要"的条数（`is_key_reason` 汇总）。"漏查了什么"靠质量门的真实事件人工抽检兜底，不靠这个指标自证。
2. **核验通过率**（未加权） = 判为"已证实"的 claim 数 / 重要 claim 总数。`is_key` 的默认判定规则：出现在执行摘要、事实核查表或时间线里的 claim 一律 `is_key=1`；模型把 claim 下调为非重要必须给出理由（`is_key_reason`），下调数量计入第 1 条的展示。
3. **加权核验通过率** = Σ(已证实 claim 的最高信源等级权重) / Σ(全部重要 claim 的最高信源等级权重)。
   > 口径注明：因"官方单源可判已证实"，未加权通过率在官方信息充分的事件上会偏高。**本公式为落实票 11 决议 2"按信源等级加权口径注明"要求的初版定义，权重值实现期可微调，但必须在报告中显示所用口径。加权口径仅用于单事件内的呈现；跨事件排名/比较在用人工标注集校准之前不启用（审查 P1 修复）。**
4. **争议率与证伪率**分开展示（审查修订：不再合并成一个"显性率"）：争议 claim 数 / 重要 claim 总数，已证伪 claim 数 / 重要 claim 总数。这两个指标都不是越低越好——它们证明产品没有把分歧抹平、也没有回避辟谣。

## 6. 合规边界

> 依据：票 04 调研（法律部分附判例与来源）、票 07 决策。**这不是免责声明，是产品能力边界的定义。**

### 6.1 默认只碰公开数据

系统默认能力仅包含：
- 搜索 API 返回的公开网页（新闻、官网、标准数据库、公开报道）；
- 公开热榜聚合（DailyHotApi 模式自部署；注意其 MIT 许可只覆盖代码，不等于上游榜单数据的许可，按"低风险但非零风险"对待，见 04 §8.2）；
- 公开数据集（逐项登记许可后接入；许可不明的默认不启用、不随本项目分发，见 04 §8.1）；
- 对公开网页的原文抓取（尊重 robots、内置频率限制）。

**默认不做**：登录态社媒内容采集、评论区批量抓取、用户关系链采集、个人身份信息（昵称/头像/手机号/账号 ID）的结构化存储与二次分发。

**数据资产登记表（审查 P1 修复）**：每个接入的数据源/数据集须登记：原始来源、采集方式、平台条款、代码许可、数据许可、可否再分发、是否含个人信息字段、缓存期限、删除机制。许可不明的默认禁用。产品对外表述统一用"较低风险、已逐源登记、持续复核"，**不做"全合规/绝对合规"的宣称**——那是一问即破的说法。

### 6.2 三条红线与判例依据（票 04 §5）

| 红线 | 法律风险 | 判例 |
|---|---|---|
| 抓取个人信息 | 侵犯公民个人信息罪（刑事） | 杭州魔蝎数据案 |
| 破解反爬 / 高频访问 | 破坏计算机信息系统罪（刑事） | 高频访问致政务网站瘫痪案 |
| 实质性替代平台服务 | 不正当竞争 | 大众点评诉百度案（判赔 300 余万）、抖音诉小葫芦案 |

**最直接的对标判例**：**微博诉蚁坊"鹰击"舆情系统案（(2019)京73民终3789号），判赔经济损失 500 万 + 合理开支 28 万**。被告是一家舆情监测工具提供商。裁判逻辑需要准确理解（审查修订：此前表述过度简化）：法院把平台数据分成公开与非公开两类——**对公开数据，法院明确表示平台应在一定程度上容忍他人合法收集利用**；蚁坊败诉的关键在于：无法证明其抓取手段正当、破坏或绕开保护措施抓取了**非公开**数据、在自己系统中改变微博的数据展示规则、给平台服务器造成额外负担，且其商业化舆情服务与微博的授权合作方构成实质竞争。换句话说，**"数据是公开的"不是护身符，法院实际审查的是手段、规模、展示方式与商业替代**。原 PRD 的"提前爬一个月社媒历史库"会踩中其中多个风险因素（所需评论/搜索数据要登录态、规模化持续抓取、本地囤积与再展示）——这是该计划被否决的直接依据。

另有：新浪微博诉脉脉案确立"三重授权"原则（用户授权平台 + 平台授权第三方 + 用户授权第三方）；微信群控软件案判赔 260 万（抓账号数据与好友关系链）。

**核心概念**：公开 ≠ 可随便抓。公开数据仍处于平台控制之下，判断要看四点：是否真正开放、手段是否合法、目的是否合法、是否造成损害。

### 6.3 Cookie 插件的边界（票 07 / 13）

深度社媒评论采集降级为**可选插件**，且必须满足：

- **默认关闭**，不随主程序启用；
- 用户在自己的环境、用自己的账号、自担风险；
- 安装/开启时展示明确的合规提示与风险声明；
- **不作为任何核心功能的依赖**——三层数据层各自独立降级，插件缺失不影响主流程（对比 BettaFish：其 InsightEngine 无库即报废，票 01）；
- 排期在 V2，V1/V1.5 完全不含此能力。

### 6.4 开源分发相关

- **不内置、不依赖**"非商业学习使用"许可的采集组件（如 MediaCrawler）作为默认能力——其许可与开源产品的商用/分发边界存在冲突（票 04 §5.6）。
- 本项目为独立实现，不复制 BettaFish（GPL-2.0）或 TrendRadar（GPL-3.0）的代码，仅借鉴设计思路，避免 GPL 传染。
  > **实现期决定**：本项目自身的开源许可（倾向 Apache-2.0，理由是专利条款对参赛/后续商业化更友好；备选 MIT）。决定时机：首次公开发布前。
- 仓库内附合规声明与免责条款，README 顶部显著位置说明"个人研究工具、不做新闻分发、输出附原文链接"。

### 6.5 内容安全降级策略

舆情事件天然涉敏。BettaFish 已出现"敏感词触发模型安全审查导致整个分析流程中断"的实际问题（票 06）。本项目的处理：

- **不学 BettaFish 的话术 hack**（在 prompt 里反复写"已通过伦理合规审查"），那是脆弱做法；
- **先分类再处置**（审查 P1 修复）：LLM 调用失败分五类——`transient`（网络/超时）、`quota`（限流/额度）、`policy_block`（模型安全策略拒答）、`privacy_block`（涉个人隐私拒答）、`unsupported`（能力不支持）。前两类走常规重试与降级链；**policy/privacy 两类不做"换模型直到有人肯答"的循环**——那构成对安全策略的规避；
- `policy_block` 的处置：至多一次"更中性的任务表述"重试（把评价性任务改写为证据比对任务），仍拒则该节点标 `blocked`，对应板块降级为"仅呈现证据原文与引用，不做综合分析"并写入局限性声明；`privacy_block` 直接进入该受限模式；
- **有稳定的政策终止态**：若多数关键节点被 policy/privacy 拦截，任务以"因内容政策终止"收尾——给出明确的说明页面与已收集证据清单，而不是反复重试拖时间烧钱；
- 全流程绝不因单点安全拦截而失败——这是"跑三小时白跑"痛点的一部分；竞赛现场的断网/全模型拒答/限流三套预案见路线图 R2/R11。

### 6.6 内容治理与个人保护（审查 P1 修复：C 端产品的名誉/隐私边界）

合规不只是"怎么抓数据"，还包括"允许用户分析什么、生成的报告怎么管"：

- **事件公共性门槛**：任务创建时由 `utility` 角色做一次公共性判定。涉及公众人物、企业/机构、公共政策、公共安全的事件正常分析；**指向可识别普通个人或未成年人的事件（人肉、私人纠纷、校园八卦式指控）拒绝生成**并返回明确理由。默认开启的硬规则，不提供关闭开关。
- **高风险指控的呈现约束**：涉未决刑事指控、重大名誉指控的 claim，只呈现权威公开材料（官方通报、判决、有采编资质媒体的报道），不生成编辑判断类内容。
- **个人信息脱敏**：证据处理与日志不结构化存储自然人联系方式、账号 ID、住址等；报告正文原则上不出现非公众人物的可识别个人信息。
- **报告生命周期**：自部署场景数据归用户所有，提供任务级删除（联动清理证据/快照/报告，架构 §6 设计说明 8）；**演示站**报告设 TTL 自动清理、公开分享默认关闭、页面提供投诉/删除入口（takedown），收到异议先下线再复核。
- 以上边界写入 README 与演示站页脚，作为产品能力边界的一部分——与 §6.1-§6.4 同级，不是免责声明。
